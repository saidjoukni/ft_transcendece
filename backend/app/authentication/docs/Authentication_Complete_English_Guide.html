Passwords, hashes, and signatures

Three separate transformations appear in this project.

OperationPurposeWhere you see it
Password hashingMake guessing a stored password expensive; verification tests a candidate.pwdlib in security.py
SHA-256 digestCompare a high-entropy reset token without storing the raw token in users.hashlib in password_reset.py
JWT signing / MACDetect changes to token contents and establish possession of the signing key.HS256 in create_access_token

Password hashing, step by step

Registration receives a password as text, unwraps SecretStr, and asks pwdlib to hash it. The library uses a random salt and cost settings; the stored representation carries what verification needs. Your dependencies include Argon2 support, and PasswordHash.recommended() selects the library’s recommended hasher. pwdlib guide

stored = hash_password("HamzaLearning2026!")
verify_password("HamzaLearning2026!", stored)  # True
verify_password("DifferentPassword123!", stored)  # False

Two users with the same password can have different stored hashes because their salts differ. The verification function uses the stored hash’s settings and salt. There is no “decrypt the hash” step.

Why SHA-256 is used only for the recovery token

A human password may be guessable. The recovery token is generated from 32 cryptographically random bytes, giving 256 random bits before encoding. A fast digest is suitable for matching that hard-to-guess token; it is not the password-storage algorithm. Python secrets

SecretStr has a smaller job

It masks normal display of a value. The original text still exists and get_secret_value() can retrieve it. SecretStr is not password hashing, encryption, or proof of identity.

What is inside your site JWT?

A signed, readable entry pass with a time limit and a session version.

HEADER.PAYLOAD.SIGNATURE

# Illustrative decoded payload, not a usable token:
{
  "sub": "42",
  "ver": 3,
  "iat": 1800000000,
  "exp": 1800001800
}
ClaimMeaning in this implementation
subLocal user ID as a string. "42" means users.id = 42.
verThe user’s auth_version when this token was issued.
iatIssue time as an integer Unix timestamp, based on UTC.
expExpiry time, 1,800 seconds after issue.
nbfOptional “not before” claim. The creation function does not add it.

The encoded header and payload can be read. HS256 creates an HMAC using JWT_SECRET_KEY, so changing sub or ver without recomputing a valid signature causes verification to fail. The payload should not contain secrets. JWT specification

decode_access_token() verifies the signature with a fixed allowed algorithm and requires all four claims. It then enforces additional claim types and ranges. get_current_user() separately checks that the database user exists and that the stored version matches.

Reading is not verification

A browser could decode text and look at exp, but it cannot establish your backend’s identity decision just by reading it. It should call a protected API such as /auth/me. Never put JWT_SECRET_KEY into frontend code.

Calling /me does not renew the token. This folder has no refresh token flow. PyJWT validation behavior

async, await, and worker threads

The request waits for its result while the server can serve other requests.

password_hash = await run_in_threadpool(
    hash_password,
    data.password.get_secret_value(),
)

hash_password is synchronous and computationally expensive. run_in_threadpool receives the function and arguments and executes it in a worker. The coroutine waits with await; it does not finish registration until the result returns. FastAPI async

WorkHow the current code runs it
User lookup and database writesAsync SQLAlchemy operations, awaited.
Password hashing / verificationSynchronous pwdlib functions dispatched with run_in_threadpool.
Google verificationSynchronous helper dispatched to a worker; may fetch Google certificates.
SMTP emailSynchronous send_email scheduled through BackgroundTasks after the response.

Waiting creates opportunities for other requests

Imagine two people registering “Hamza42.” Both can pass an early lookup before either finishes hashing. Only the database’s unique constraint decides which insert can commit. Likewise, password verification can overlap a password reset, so authenticate_user refreshes the stored user before accepting the earlier check.

Background does not mean guaranteed

BackgroundTasks runs work associated with the response in the application process. It is not a durable queue. A process failure can lose pending email, and send_email has no retry loop. FastAPI background tasks

A useful reading rule

An await marks a place where this coroutine may give other work a turn. Ask which assumptions could change before it resumes. A thread pool keeps blocking work off the event loop; it does not create unlimited capacity.

Transactions, uniqueness, and atomic updates

Why checking once in Python is not enough under concurrency.

A transaction groups database work until commit or rollback. commit makes the successful write durable; rollback abandons the transaction’s changes. A session coordinates this work for a request. SQLAlchemy does not turn every Python assignment into a committed database write immediately.

Expression in the codeWhat happens
select(User).where(...)Build a query; it is executed when passed to the session.
await db.scalar(query)Execute and return the first column of the first row, or None. For select(User), that is a User object.
db.add(user)Place a new ORM object in the session for insertion.
await db.commit()Flush pending changes and commit the transaction.
await db.rollback()Discard transaction work and restore a usable session after failure.
await db.refresh(user)Read current stored column values back into the existing object.
update(User).where(...).values(...).returning(User.email)Update only rows meeting the condition and return the changed email.

The reset token is consumed with one database operation

The final reset UPDATE checks identity, digest, and expiration at the same time as changing the hash, clearing the token, and increasing auth_version. Two requests cannot both consume the same stored digest successfully. A separate SELECT followed by an unconditional UPDATE would leave a race.

The boundaries are specific

The reset transaction protects token consumption and the version change. It does not undo API actions already authorized before the reset committed, and it does not make all other requests globally sequential.

General session behavior: SQLAlchemy async ORM. The exact transaction decisions above come from your repository and reset functions.

Why the login password rule is different

Registration and reset choose a new password and enforce the full policy. Login checks an existing password against the stored verifier. Requiring a new-password policy there could reject a historically valid password before verification is attempted.

password_policy = (
    PasswordValidator()
    .has().uppercase().has().lowercase()
    .has().digits().has().symbols()

The minimum and maximum password lengths come from Field, not from this policy chain. The chain checks categories and absence of spaces. A field validation failure raises a request validation error, which AuthRoute returns as a sanitized 422.

Response models keep the public contract small

schemas.py · all three validation functions

These functions reject bad input; they do not create users or sessions.

validate_password_encoding(value)

Receives: A SecretStr after basic type/field processing.

Steps: Unwrap the value and attempt UTF-8 encoding. Return the same object when encoding works.

Returns or raises: SecretStr, or ValueError with a safe message if UnicodeEncodeError occurs.

Why it exists: Reject malformed Unicode text, such as an unpaired surrogate, before a hashing library tries to encode it.

RegisterData.validate_username(cls, username)

Receives: A username that has already met the 3–15 character field length constraint.

Steps: Require username[0].isalpha() and username.isalnum(). Return the original text.

Returns or raises: The unchanged str, or ValueError.

Why it exists: Keep accepted names aligned with the application’s letter-first, letters-and-numbers policy.

RegisterData.validate_password_complexity(cls, value)

Receives: The candidate SecretStr password.

Steps: Unwrap the password and ask password_policy.validate(...) to check required character categories and spaces.

Returns or raises: The original SecretStr, or ValueError describing the policy.

Why it exists: Share one complexity rule between registration and ResetPasswordData.validate_password().

repository.py · create_user()

The place where account creation becomes persistent.

create_user(db, username, email, password_hash, *, google_sub=None)

Receives: An AsyncSession, account display fields, a hash or None, and optional keyword-only Google subject.

Steps: Construct User, which triggers ORM identity normalization. Add it to the session. Await commit. On IntegrityError, rollback; if the original PostgreSQL SQLSTATE is 23505, raise DuplicateUserError, otherwise re-raise the database error.

DuplicateUserError is a domain-level exception

The class only subclasses Exception; pass adds no methods. The repository raises it to mean “account uniqueness conflict.” Routes translate it into HTTP 409, so low-level database details are not the public API contract.

Why rollback is needed

A failed transaction cannot simply be treated like a successful write. Rolling back discards failed work and resets the session’s transaction state. Only the 23505 uniqueness case becomes DuplicateUserError; a different constraint or infrastructure error is not mislabeled a duplicate.

AsyncSessionLocal is configured with expire_on_commit=False in dataProcessing/database.py. This lets normal loaded attributes remain available after commit. The repository returns the User so the route can construct its response.

What changes, and what does not

The raw token is never written into the users table. The digest and expiry are cleared after success, while reset_sent_at remains to enforce the recent-issue cooldown. No new JWT is created and no cookie is refreshed or explicitly cleared by this route. The user must log in with the new password.

Google sign-in, OAuth, and OIDC

Learn the names without adding imaginary steps to your code.

OAuth 2.0 is an authorization framework: a person can grant an application permission to call another service. OpenID Connect adds a standardized identity layer and ID token. Sign-in and permission to read Google data are different decisions. OpenID Connect

TermWhat to understand here
ID tokenA provider’s statement about a user, intended for a particular application. Your credential from Google is an ID token.
Access tokenA credential accepted by an API. Your backend calls its locally issued JWT access_token.
Refresh tokenA credential that may obtain new access tokens. This backend has no refresh-token endpoint.
Client IDPublic identifier of the Google application configuration. The frontend ID should match the backend audience.
ScopeA named permission, such as access to some external API data. This app does not request Gmail-reading access in its shown sign-in flow.
Authorization codeIn another common OAuth/OIDC flow, a short-lived code is exchanged for tokens. That exchange is absent here.
state / nonce / PKCEProtocol mechanisms used to bind attempts or protect code exchanges in applicable flows. They are not the same thing as Google’s g_state cookie.

The actual chain in your app

Google sign-in UI
  -> response.credential (Google ID token)
  -> POST /auth/google
  -> verify_google_token
  -> find/create local User
  -> create_access_token(local id, auth_version)
  -> access_token cookie + JSON
  -> protected site APIs
Do not swap the two credentials

A Google ID token is verified using Google’s keys and your client ID. The site JWT is verified using JWT_SECRET_KEY and then the local user/version. They have different issuers and purposes.

Follow a recovery link from email to API

The URL fragment and the POST body have different jobs.

# Configured frontend destination (illustration)
PASSWORD_RESET_URL=http://127.0.0.1:3000/login?mode=reset-password

# Email link created by forgot_password
http://127.0.0.1:3000/login?mode=reset-password#token=RANDOM_TOKEN
  1. A visitor submits {"email":"hamza@example.com"} to POST /auth/forgot-password. An eligible account gets a background email attempt; the frontend receives generic 202.
  2. The browser opens the frontend URL. The #token fragment is not part of the HTTP request sent to fetch that page. Frontend JavaScript can read it from window.location.hash.
  3. captureToken stores the value in memory and removes the fragment from the visible URL. The page asks for a new password and a matching confirmation.
  4. The frontend submits the token explicitly in JSON to POST /auth/reset-password. The backend hashes it to locate the stored digest, validates expiry, and atomically consumes it.
  5. On success, the frontend clears its token/password state and opens /login?passwordReset=success. The user signs in with the new password; previous JWT versions fail.
POST /auth/reset-password
Content-Type: application/json

{"token":"ACTUAL_43_CHARACTER_TOKEN_FROM_THE_LINK",

The token text above is a descriptive placeholder. It is not a valid 43-character recovery token and must be replaced for a real request.

Where sensitive values travel

The raw token exists in the email, the browser URL/memory, and the reset POST body. Only its digest is stored in users. The fragment reduces automatic URL transmission to the frontend server, but JavaScript on that page can still access the token.

“I see a cookie, but I am not logged in”

Presence is only the first step in validation.

  1. Check the host where the cookie is stored. A cookie set for localhost is not automatically a cookie for 127.0.0.1. Use one hostname consistently.
  2. In the Network panel, inspect the actual /auth/me request. apiFetch includes credentials, but a different raw fetch call might not.
  3. Check the response code. 401 means this request did not pass the site’s authentication checks. A cookie can contain an expired, tampered, old-version, or otherwise unacceptable token.
  4. Look for an Authorization header. Parsed Bearer credentials take precedence over the cookie; an old header token may be the token being rejected.
  5. Check whether the backend secret changed, the user was removed, or a password reset incremented auth_version. All can explain rejection.
  6. If /me succeeds but navigation reaches a 404, check whether the target page exists. /join is the current default, and its page is absent from this checkout.

“Why does document.cookie not show access_token?”

It is HttpOnly. The browser may show it in DevTools while hiding its value from page JavaScript. That is expected. /auth/me is the frontend’s way to ask whether the session is accepted.

“Does g_state tell my app that I am logged in?”

No authentication function here reads g_state. Google uses it for its own sign-out/automatic-sign-in behavior. It neither verifies the local JWT nor replaces the access_token cookie. Your current Google component also does not implement site logout.

Check a protected page and a protected API separately

A frontend guard decides what the visitor sees. The backend dependency decides whether a data request may proceed as a particular user. Both need the right behavior; hiding a page does not secure its APIs.

Answers · identity and sessions

Questions 1–8

  1. 401. register creates a database row but does not issue a JWT. get_current_user sees no credential and raises unauthorized().

Answers · concurrency and recovery

Questions 9–16

  1. The first query avoids wasted hashing; the final UPDATE makes the decision. The token can expire or be consumed while hashing runs. The UPDATE rechecks it and changes state atomically.
  2. A race can occur before commit. Both requests see no user and begin hashing. Database uniqueness prevents both normalized identities from being inserted successfully; create_user maps the unique violation.
  3. Several explanations fit 202. No matching account, a Google-only account, cooldown, missing SMTP settings, delivery failure, or a process interruption after the response. The public message intentionally does not disclose eligibility.
  4. 422 versus 400. Bad length/characters fail ResetPasswordData validation. A correctly shaped token reaches digest/expiry checking, which returns 400 when no eligible state matches.
  5. The HTTP caller need not wait for SMTP. BackgroundTasks delays that work until after the response. It does not guarantee delivery or provide durable retries.
  6. It ignores a late response after the effect was cleaned up. It prevents an obsolete fetch result from updating that component/redirecting through that effect. It does not cancel the network request itself.
  7. The browser is controlled by the caller. They can bypass the screen and call an API. The backend must validate credentials and check ownership/permissions on protected operations.
  8. Not automatically. PostgreSQL retains user/version state. A token can work after restart when the same signing secret is used and the user, version, claims, and expiration still pass.
